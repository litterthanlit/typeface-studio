# Setting Inter for body/UI text and pairing it with a separate headline face (Inter 4.x, as of Oct 2026)

Method note: primary sources were read in full where possible: the archived Dynamic Metrics page and its JavaScript, rsms.me/inter, the Inter README and the help.txt that ships with the font, and live production CSS from Linear, Tailwind, Catalyst, Notion, Raycast, Radix and Cal.com, downloaded with curl on 2026-10-19. Items marked "own measurement" were computed by me. I used fontTools 4.67 on the shipping font files: InterVariable.woff2 v4.001 from rsms.me, Inter v20 (4.001) and Hanken Grotesk v12 (3.013) from Google Fonts, and 12 other Google Fonts grotesks. I also rendered them in Playwright Chromium 141.0.7390.37 with canvas pixel counting. These numbers can be reproduced from the cited font URLs.

## Q1. Inter "Dynamic Metrics": constants, formula, and the resulting values (historical Inter 3 guidance)

### Takeaway
Rasmus Andersson's Dynamic Metrics formula, checked against the page's own source code, is **tracking (em) = −0.0223 + 0.185 × e^(−0.1745 × size_px)** and **line-height (px) = round(1.4 × size_px)**. Tracking crosses zero at about 12px, is −0.0088em at 15px and −0.0128em at 17px, and levels off at about −0.022em from 32px up. Dynamic Metrics was written for Inter 3, which had no optical-size axis. The current Inter 4 site has removed the page (it now returns a "page used to exist, but is no longer" 404). Treat it as **historical guidance**. In Inter 4 the opsz axis builds part of this tightening into the font (see Q2).

### Cited Findings
- Formula as stated on the page: "You simply provide the optical font size, and the tracking and line height is calculated for you through the following formula: tracking = a + b × e^(c × z); line height = 1.4 × z; a = -0.0223, b = 0.185, c = -0.1745, z = font size" — [Inter Dynamic Metrics (archived v3 site)](https://d.rsms.me/inter-website/v3/dynmetrics/)
- The page's JavaScript confirms the constants: `var a = -0.0223, b = 0.185, c = -0.1745 // 2019-02-07` and `var l = 1.4`. Tracking is `a + b * Math.pow(Math.E, c * fontSize)` in em, and line height is `Math.round(fontSize * l)` in px. A code comment says "weightClass is currently unused", so the formula does not change with weight. CSS output is `letter-spacing: <tracking rounded to 3 decimals>em` and `line-height: <px>` — [Dynamic Metrics page source](https://d.rsms.me/inter-website/v3/dynmetrics/)
- The same source keeps the superseded constant sets as comments (historical): a=−0.012, b=0.23, c=−0.21 (2018-02-18); a=−0.0149, b=0.298, c=−0.23 (2018-02-19); a=−0.017, b=0.202, c=−0.175 (2018-09-28); a=−0.02, b=0.0755, c=−0.102 (2019-02-02); a=−0.038, b=0.161, c=−0.12 (2019-02-06). An older fitted curve also appears in a comment: "y = -0.01021241 + 0.3720623 * e ^ (-0.2808687 * x)". Some third-party copies of the formula may carry these older constants. Only the 2019-02-07 set is active — [Dynamic Metrics page source](https://d.rsms.me/inter-website/v3/dynmetrics/)
- Rasmus's hand-tuned "ideal values" (2019-02-07), which the curve was fitted to, in em: 6: 0.043, 7: 0.032, 8: 0.024, 9: 0.016, 10: 0.01, 11: 0.005, 12: 0, 13: −0.0025, 14: −0.006, 15: −0.009, 16: −0.011, 17: −0.013, 18: −0.014, 20: −0.017, 24: −0.019, 30: −0.021, 40: −0.022, 80: −0.022 — [Dynamic Metrics page source](https://d.rsms.me/inter-website/v3/dynmetrics/)
- Framing on the page: "There's of course no absolute right or wrong when it comes to expressing yourself with typography, but Inter Dynamic Metrics provides guidelines for how to best use Inter." — [Dynamic Metrics (archived)](https://d.rsms.me/inter-website/v3/dynmetrics/)
- Status: https://rsms.me/inter/dynmetrics/ now serves "404 not found — This page used to exist, but is no longer. You can visit an archived version of the old website" (noindex), linking to the v3 archive — [rsms.me/inter/dynmetrics](https://rsms.me/inter/dynmetrics/)

- Taken literally, Dynamic Metrics would track litt.md's Inter sizes 0.003–0.010em tighter than now: −0.0128 vs −0.006 at 17px, −0.0088 vs −0.003 at 15px, −0.0032 vs 0 at 13px, +0.0005 vs +0.01 at 12px. Corrected for Inter 4's automatic opsz tightening, though, litt.md's reading size (−0.006em at 17px) sits **inside** the equivalent band (−0.005 to −0.008em). Body at 15px (−0.003) is about 0.003–0.004em looser than the equivalent (−0.006 to −0.007). Small (13px, 0) and caption (12px, +0.01) are looser than Dynamic Metrics because opsz does nothing below 14px.
- DM's 1.4× line height is a single generic UI rule with no adjustment for long-form reading. litt.md's 1.55 at 15px and 1.65 at 17px are deliberately airier. That is defensible for paragraphs (see Q4). DM gives no basis for a line-height that varies with size, while litt.md's headings tighten to 1.1–1.3. Most systems in Q4 do the same, but that is common practice, not Inter guidance.
- Dynamic Metrics does not apply to Hanken Grotesk. The heading rows are only a reference for "what Inter would do at that size" (see Q6 for a Hanken translation).

### Gaps
- I found no statement from Rasmus Andersson on why Dynamic Metrics was dropped from the v4 site, or on whether it should be used with Inter 4's opsz axis. The "residual" column is my derivation, not his guidance.
- Dynamic Metrics ignores weight and polarity. There is no official guidance for tracking at 350–380 or in dark mode.

## Q2. Inter 4.x optical sizes: opsz range, what changes, browser auto-application, Google Fonts, when to use Inter Display

### Takeaway
Inter 4's opsz axis runs 14 to 32, with "text" at 14 and "display" at 32. Display has a lower x-height (0.516 vs 0.546em), narrower glyphs, and much tighter built-in spacing: sidebearings are 0.028em per glyph smaller at opsz 32. Browsers apply opsz automatically from the CSS px font-size (`font-optical-sizing: auto` is the initial value). In Chromium the value is clamped to the 14–32 range, so 12–14px text uses the text design and text at 32px and up uses the full Display design. Google Fonts serves Inter with the opsz axis, but its build strips nearly all stylistic features. "Inter Display" is only needed as a separate family when you use static fonts. The variable font reaches it automatically at 32px and above.

### Cited Findings
- Technical details on the official site: "UPM: 2048; Variable axis opsz [14–32]; Variable axis wght [100–900]; Constant axis ital [0, 9.4°]; Style classification: Sans-serif, Grotesk; x-height, opsz=14: 1118 UPM; x-height, opsz=32: 1056 UPM; Cap height: 1490 UPM; Ascender: 1984 UPM; Descender: -494 UPM" — [rsms.me/inter FAQ](https://rsms.me/inter/)
- What changes, per the designer: "The smaller 'text' optical-size designs features a tall x-height to aid in legibility of lower-case text, with several contrast-enhancing details like ink traps and bridges. The larger 'display' optical-size designs offers clean lines, smooth curves and delicate details for excellent rhythm of large text." Also: "Each glyph has three dedicated designs for weights 100, 400 and 900" — [rsms.me/inter](https://rsms.me/inter/)
- Inter 4.0 introduced "Six additional 'Display' designs, assigned to an `opsz` variable-font axis", "exposed as a second family 'Inter Display' as static fonts", along with "UPM changed to 2048, refined metrics" — [Inter v4.0 release](https://github.com/rsms/inter/releases/tag/v4.0)
- The distribution's help.txt: "Variable fonts is a new format which allows you to choose any weight and optical size… Inter's variable font is called 'Inter Variable'… Static fonts … uses a fixed set of predefined mixtures of weight and optical size. For example 'Inter Display Medium' is Inter with maximum optical size and a weight of 500." — [Inter help.txt (mirror of the 4.x distribution file)](https://momjian.us/main/font/inter/help.txt)
- The official CSS (https://rsms.me/inter/inter.css) defines the families `Inter` (static), `InterDisplay` (static, 18 @font-face rules), `InterVariable`, and a legacy `'Inter var'` alias. The site's recommended snippet is `:root { font-family: Inter, sans-serif; font-feature-settings: 'liga' 1, 'calt' 1; /* fix for Chrome */ } @supports (font-variation-settings: normal) { :root { font-family: InterVariable, sans-serif; } }` — [rsms.me/inter](https://rsms.me/inter/), [inter.css](https://rsms.me/inter/inter.css)
- Own measurement (fontTools, InterVariable.woff2 4.001 at wght 400). Values are per glyph, averaged over the letters of "The quick brown fox jumps over the lazy dog". Opsz 14 → 32: advance 0.5461 → 0.4994em (−8.6%); sidebearings L+R 0.1062 → 0.0778em (−0.0284em); glyph bounding-box width 0.4400 → 0.4216em; space 0.2812 → 0.2500em; x-height 0.546 → 0.516em; cap height unchanged at 0.7275em; 'I' stem 0.0928 → 0.0879em. Intermediate sidebearing deltas against opsz 14: opsz 15 −0.0015, 16 −0.0032, 17 −0.0047, 20 −0.0094, 24 −0.0158, 28 −0.0221. Advance deltas: 15 −0.0026, 16 −0.0052, 17 −0.0078, 20 −0.0156, 24 −0.0260, 28 −0.0364, 32 −0.0468em. Ink density is nearly constant across opsz (0.1932 → 0.1926) — [InterVariable.woff2 v4.1](https://rsms.me/inter/font-files/InterVariable.woff2?v=4.1)
- Own measurement: the variable font's fvar named instances are only the 9 text instances (opsz 14, wght 100–900). There are no named Display instances in the variable font, so Display is reached through the axis — [InterVariable.woff2 v4.1](https://rsms.me/inter/font-files/InterVariable.woff2?v=4.1)
- MDN: `font-optical-sizing` initial value is `auto`; "Optical sizing is enabled by default for fonts that have an optical size variation axis"; `auto`: "The browser will modify the shape of glyphs for optimal viewing"; Baseline "Widely available… since March 2020" — [MDN font-optical-sizing](https://developer.mozilla.org/en-US/docs/Web/CSS/font-optical-sizing)
- Own measurement in Chromium 141. I measured the width of a 54-character string in InterVariable with `auto`, with `none`, and with `opsz` forced to 14 or 32. At 12 and 14px, auto = none = forced 14 (clamped). At 16px auto was 0.9% narrower than none. At 20px 2.7%, at 24px 4.5%, and at 28px 6.3% narrower. At 32 and 40px, auto = forced opsz 32 (8.1% narrower than none). So Chromium sets opsz = CSS px font-size, clamped to 14–32. Canvas `fillText` also applies auto opsz — [own Playwright test with InterVariable.woff2](https://rsms.me/inter/font-files/InterVariable.woff2?v=4.1)
- CSSWG archive: a 2019 Chrome implementer reported Safari, Firefox and Chrome all map auto opsz to CSS px. A 2020 commenter argued the intended mapping is points (0.75 × px). Per the search summary of these threads, zoom handling differed: Firefox ignores zoom, Chrome and Safari scale with it — [public-css-archive 2019-10](https://lists.w3.org/Archives/Public/public-css-archive/2019Oct/0423.html), [public-css-archive 2020-06](https://lists.w3.org/Archives/Public/public-css-archive/2020Jun/0691.html)
- Google Fonts: the CSS2 API accepts `family=Inter:ital,opsz,wght@0,14..32,100..900;1,14..32,100..900` and serves variable Inter v20 (name table "Version 4.001"), roman and italic, at weights 100–900 — [Google Fonts CSS API response](https://fonts.googleapis.com/css2?family=Inter:ital,opsz,wght@0,14..32,100..900;1,14..32,100..900)
- Own measurement: the Google Fonts latin Inter file contains only these GSUB features: calt, ccmp, dnom, frac, locl, numr, pnum, tnum. It has **no cv01–cv14, ss01–ss08, zero or case**. The rsms.me file has all of them. - A developer report agrees: Inter loaded via `next/font/google` did not expose the alternates, and self-hosting the GitHub build fixed it — [DEV Community](https://dev.to/heygauravshukla/why-the-same-font-can-look-so-different-and-how-to-fix-it-2kfg). A Figma forum thread reports some Inter features missing in the Google Fonts version — [Figma forum](https://forum.figma.com/ask-the-community-7/new-inter-and-inter-display-open-type-features-are-not-showing-up-in-figma-25231)
- The Inter README says: "Should I use Inter from Google Fonts? No, unless you have no other choice. (outdated, no italics)". The italics part is now out of date, since Google Fonts serves italics (see above). The feature stripping is current — [Inter README](https://github.com/rsms/inter/blob/master/README.md)
- Requesting `family=Inter+Display` from the Google Fonts CSS API returned an error page, not CSS. On Google Fonts, Display is reached through the opsz axis of `Inter` — own test against [fonts.googleapis.com](https://fonts.googleapis.com/css2?family=Inter+Display:wght@400)
- When to use Inter Display, per brand guidance: GoCardless says "Use Inter Display for large headings and display text. It's optimized for larger sizes with tighter spacing" and "Use Inter Display only for headings 24px and above". Its scale uses Inter Display at 64px (−3%) and 32px (−2%), but plain Inter at 28px and below — [GoCardless brand: Typography](https://brand.gocardless.com/typography). - Linear sets `--font-variations: "opsz" auto` with Inter Variable 4.1, so its 32–72px titles automatically get the Display design — [linear.app CSS](https://linear.app/)
- README history: "Early versions of Inter was not suitable for very large sizes because of some small-scale glyph optimizations (like 'pits' and 'traps')… a Display subfamily is in the works" — [Inter README](https://github.com/rsms/inter/blob/master/README.md)

### Inferences
- With the variable font and default CSS, you rarely need to choose Inter Display yourself: at 32px and up you get it automatically, and between 14 and 32 you get an interpolated design. Static `InterDisplay` matches the variable font only at ≥32px. Using it at 20–28px gives a lighter, tighter look than auto-opsz would.
- Inter 4's opsz already builds in tightening equivalent to −0.0047em of spacing at 17px, −0.016em at 24px, and −0.028em at 32px and up. That is more than Dynamic Metrics' −0.022em asymptote. **Applying Dynamic Metrics tracking on top of auto-opsz therefore over-tightens from about 24px up.** Systems like Linear (−0.022em plus opsz auto at 32px+) end up tighter than Dynamic Metrics ever specified. That is a stylistic choice, not Inter's guidance.
- For litt.md, Inter only sets 12–17px, so opsz effects are small. 12–13px get pure text Inter. 15px gets opsz 15 (−0.0026em advance per glyph). 17px gets opsz 17 (−0.0078em advance), with x-height 0.541 instead of 0.546. To pin body text to the text design, set `font-optical-sizing: none` or `font-variation-settings: 'opsz' 14`. Pinning would make the "DM-literal" column the right comparison.
- Loading Inter from Google Fonts makes any cv/ss/zero/case choices in Q3 silently inert. Self-host the rsms.me 4.1 files, or the GitHub release, if features matter.

### Gaps
- I could not read Google Fonts Knowledge articles on optical sizing. The pages render client-side and returned no text to WebFetch or headless Chromium.
- I could not confirm current Safari behaviour (px vs pt mapping for opsz on macOS 15/26). A search result mentioned a report that Safari on macOS 14 used pt, but I could not trace the primary source.
- I found no explicit Rasmus Andersson guidance on a px threshold for Inter Display. The 24px (GoCardless) and 30px (Auckland) thresholds are brand conventions.

## Q3. Inter's OpenType features for product UI, and which ones real products enable

### Takeaway
Inter 4.1 has 14 character variants (cv01–cv14) and 8 stylistic sets (ss01–ss08), plus tnum, zero, case, frac, sups/subs and others. calt and ccmp are on by default. Common product choices are cv11 (single-storey a: Tailwind, Catalyst), cv01 (alternate 1) with ss03 (round quotes and commas) at Linear, and cv02/cv03/cv04 open digits at Tailwind. Products also apply tnum and zero to numbers selectively (Linear's slashed-zero utility). None of these work with the Google Fonts build.

### Inferences
- A defensible product-UI set for litt.md body: keep calt on (default). Consider cv11 for a friendlier, more geometric a, which may also sit better next to Hanken Grotesk's forms; this is a visual judgement I have not verified. Add tnum plus zero, or ss02/ss04, only in data, code and ID contexts, and case for all-caps labels. Use cv05 (l with tail) or cv08 (I with serif) where Il1 confusion matters, such as tokens, codes and passwords. ss03 makes quotes and commas round; Linear and Raycast use it.
- cv11 widens "a" by about 9% in my measurement, which slightly lengthens text. Enable it before final line-length and tracking tuning.
- Hanken Grotesk's Google Fonts build has no tnum or case (see Q6). Use Inter, not Hanken, for numeric UI such as tables, stats and timestamps, even at heading sizes.

## Q4. Body sizes, line heights and tracking used with Inter in product UI and long-form; failure modes; x-height and leading

### Takeaway
Production Inter systems set UI body at 14–16px with line-height 1.43–1.6 and tracking between 0 and −0.013em, and long-form at 16–18px with 1.5–1.65. Dynamic Metrics' 1.4× is the tight end. Inter's x-height is tall (0.546em at opsz 14). The same line-height ratio therefore leaves less white space between lines in x-height terms than it would for a lower-x-height face. ### Inferences
- Line-height in x-heights, from Inter's 0.546em text x-height: 1.4 ≈ 2.56 x-heights, 1.5 ≈ 2.75, 1.55 ≈ 2.84, 1.6 ≈ 2.93, 1.65 ≈ 3.02. A face with Hanken's 0.493em x-height gets the same 2.84 x-heights at 1.40. So litt.md's 15/1.55 Inter body has the same interline proportion as a typical lower-x-height grotesk at 1.40. 17/1.65 (3.02 x-heights) is on the generous side and suits long-form. Both are within the band that production Inter systems use for reading text (Linear 1.6, GoCardless 1.6).
- Likely failure modes, inferred from the sources above:
  - **Too loose tracking** (0 or positive at 15–17px): Inter's wide text spacing (sidebearings 0.106em per glyph at opsz 14) starts to look gappy and words lose shape. Dynamic Metrics exists because zero tracking above about 12px is looser than the designer intended.
  - **Too loose leading** (>1.7 at body sizes): lines lose cohesion, making the return sweep harder (Stuff & Nonsense).
  - **Too tight** (≤1.35 with long lines): the tall x-height crowds the lines.
  - **Too heavy**: Inter 400 is already among the darkest contemporary grotesks per unit area (Q5). Raising body text to 450–500 makes paragraphs dense. GoCardless reserves 500/600 for UI emphasis and headings.
- Production systems mostly track Inter body at about −0.01em at 14–16px (Linear −0.011 to −0.013, GoCardless −0.01, Dynamic Metrics −0.006 to −0.011). Notion uses 0, but on Inter 3 without opsz. litt.md's −0.003em at 15px is at the loose end of this band.

### Gaps
- I found no controlled study of Inter-specific reading performance by line-height or tracking. All guidance here is designer convention.
- I found no measured statement from Rasmus about long-form (16–18px paragraph) leading beyond the generic 1.4× rule.

## Q5. Inter's apparent weight and width at 400 vs other grotesks; lighter variable weights (350–380); Windows and dark-mode risks

### Takeaway
By vector ink area, Inter 400 (text) is about 6.6% darker than Hanken Grotesk 400 (7.9% in rasterized Chromium measurement) and about 6.4% wider. Inter at about 365–370 matches Hanken 400's darkness, confirming the earlier in-browser finding. Inter 400 is about as dark as Arimo (Helvetica/Arial metrics) and darker than DM Sans, Figtree, Instrument Sans, IBM Plex Sans and Hanken by 6–9%. Teams do use non-standard variable weights (Linear: 510/590/680). I found no production system that sets Inter body below 400 in light mode, and GoCardless forbids it. Thinner body text is mainly recommended for dark mode, because light text on dark looks heavier. Weights of 350–370 give stems of about 1.0–1.2 CSS px at 13–15px. Inter's variable fonts and web fonts are unhinted, which is a real risk on 1× Windows displays.

- If litt.md wants Inter body to match Hanken headings in colour, about 365–370 is the measured match. That is a 6–8% reduction in ink. But the headings are much larger, so a body/heading colour match matters less than body text's own legibility. Inter body is normally *meant* to be slightly darker than a same-weight display face.
- Risks at 350–370 in light mode: stems fall to about 1.0–1.2 CSS px at 13–15px. On 1× Windows displays with unhinted variable web fonts, these render as low-contrast gray strokes, especially for 12–13px small and caption text, and grey text colours make it worse. - If Windows 1× rendering is a priority, consider the hinted static web fonts (extras/woff-hinted), which lose opsz, or keep body at 400.

## Q6. Pairing a separate headline face with Inter body: examples, principles, Hanken Grotesk metrics, and tuning so they read as one system

### Takeaway
Real systems that keep Inter for body or UI and add a headline face include Linear (Inter Variable plus Tiempos Headline serif display), GoCardless (Inter and Inter Display plus Haffer XH secondary), and Cal.com (Cal Sans headlines; its live site has now moved body to Cal Sans UI). Pairing guidance favours faces that are identifiably different but similar in x-height, weight and curves, and Hanken Grotesk at 400 is close to Inter in proportions. Measured against Inter, Hanken's x-height is 9.7% lower than Inter text and 4.4% lower than Inter Display, its x/cap ratio of 0.707 is almost identical to Inter Display's 0.709, its average glyph width matches Inter Display's, its spacing sits between Inter text and Display, and it is about 6% lighter. Translating Inter's Dynamic Metrics to Hanken's metrics suggests about −0.008 to −0.017em at 32–40px, looser than litt.md's −0.022 to −0.025em.

### Inferences
- **How the pair relates.** Hanken 400 over Inter body is a low-contrast sans/sans pairing, which Butterick says can work better than high contrast. Hanken's proportions are almost those of Inter Display: the same x/cap ratio and the same average glyph width, with a 4% lower x-height, 4% shorter caps, looser spacing and about 6% less ink. The two will read as close relatives. The differentiators are construction details (Hanken's tailed l, its forms), not width or x-height. If more separation is wanted, the levers are weight (e.g. Hanken 500–600 for headings: measured ink 1.04–1.16× Inter 400) or size steps. Width is not a lever here.
- **Size matching.** At equal font-size, Hanken's x-height is 0.90× Inter text. A Hanken heading at 20px has an x-height of 9.9px, while Inter body at 17px (opsz 17) has 9.2px. The h4/reading step is therefore only 1.07× in x-height terms, even though it looks like a 1.18× step in px. Consider this when judging whether h4 separates enough from reading text. Bigger steps (h3 24px: 11.8px x-height) are clear.
- **Translating Inter's tracking guidance to Hanken headings.** Target per-glyph spacing at size z = Inter text sidebearing (0.1062em) + DM(z). The Hanken letter-spacing that reaches that target:
  - On an absolute-em basis: 17px +0.001, 20px −0.003, 24px −0.006, 28px −0.007, 32px −0.008, 40px −0.008em.
  - Normalized to x-height (Hanken spacing scaled so spacing/x-height matches Inter's): 20px −0.010 to −0.012, 24px −0.012 to −0.014, 28px −0.012 to −0.016, 32px −0.012 to −0.016, 40px −0.012 to −0.017em.
  - Against litt.md, compared with the x-height-normalized band: display 40 at −0.025em is about 0.008–0.013em tighter. h1 32 at −0.022em is about 0.006–0.010em tighter. h2 28 at −0.02em is about 0.005–0.008em tighter. h3 24 at −0.018em is about 0.004–0.006em tighter. h4 20 at −0.012em sits at the tight edge of the band, about 0.001em beyond it. Against the absolute-em basis, every heading is tighter still.
  - Interpretation: litt.md's heading tracking follows Linear/Notion-style "tight display" practice, not Inter-equivalent spacing. This is a deliberate aesthetic and fine at 400 weight with large sizes. But if "reads as one system with Inter body" is the goal, easing display and h1 to about −0.015 to −0.018em would bring Hanken's spacing rhythm in line with what Inter's own curve, or Inter Display, would produce.
- **Line-height between the faces.** Hanken's ascender and descender box (1.303em) is taller than Inter's (1.21em). At litt.md's heading line-heights of 1.1–1.25 the half-leading is negative, so the glyph box overflows the line box. Fixed headings should be checked for clipping of descenders and ascenders in tight containers. Never use `line-height: normal` across both faces, because it gives 1.30 vs 1.21.
- **Numerals.** The Google Fonts build of Hanken has no tnum. Headings containing changing numbers (counters, prices) will jitter. Set those in Inter with tnum, or self-host a fuller Hanken build if one exists (unverified).

### Gaps

- I could not access Typewolf or Smashing articles specifically on sans/sans pairing. The principles above come from Butterick and Adobe.
- Cal.com's earlier Cal Sans + Inter body setup, the pattern often cited, could not be confirmed from an official current source. The live site has moved body text to Cal Sans UI.
